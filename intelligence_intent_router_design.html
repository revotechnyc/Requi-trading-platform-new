Intelligence Intent Router
Design Specification — Implemented Edition

One chat, three modes, zero confusion. A deterministic router decides — in code — whether a message is conversation, a trade intent, or an order command. Trade intent triggers the advisory-first pipeline: analyze the market, check the protocol, deliver a verdict (favorable / unfavorable / wait), then stage a ticket. The model narrates; the router decides. Includes implementation guide, acceptance tests, and the addendum of what shipped in snapshot 4896a72.

1The problem, in the user's own words

The Intelligence chat cannot hold two thoughts at once. Today it behaves like this:

User: "buy Apple" SYMPTOM 1

Intelligence: locks into trade mode — asks for quantity, stop, ticket strings. Every follow-up question ("wait — why that stop?", "actually what do you think of the market today?") is treated as more trade input. There is no way back to a normal conversation without abandoning the thread.

User: "what do you think about this market, should I be buying here?" SYMPTOM 2

Intelligence: has a lovely conversation — and never touches the trade tools. The user who then says "okay, do it" often gets more conversation instead of a staged ticket.

The required behavior (the product owner's words, cleaned up): the default is intelligence — a real conversation. But when the message carries a trade trigger, the system must switch modes deliberately: before anything is staged, it analyzes the market, checks against the protocol, and tells the user whether it's a good buy, a bad buy, or when to buy — and only then moves toward a ticket. The switch between chatting, buying, and selling must be explicit and code-driven, not a vibe the model is having.

Design principle (unchanged house rule)
The model narrates; code decides. Mode selection is a decision — therefore it moves from the prompt into the router, where it is deterministic, testable, and auditable. This is the same separation the rest of the platform already enforces: AI proposes, code disposes.

2Root cause: the model is currently the router

The Intelligence runtime is well-built — live state snapshot, whitelisted tools, a single write tool (proposeTrade) that lands in the same confirmation gate as everything else. The defect is one layer up: nothing in code decides what kind of message arrived. The system prompt's Rule 2 ("when the user expresses a trade… extract… ask… only then call proposeTrade") is advice to the model, and like all prompt-layer rules it is probabilistic:

What should happenWhat governs it todayWhy it fails
Recognize "buy X" as trade intentModel judgment under a 2,000-word system promptOver-trigger: trade framing hijacks the whole thread — the model keeps extracting parameters instead of conversing
Stay conversational by defaultModel judgmentUnder-trigger: in a conversational flow the model never reaches for the tool, even when the user says "do it"
Analyze before stagingSuggested, not sequencedNothing forces market analysis → protocol check → verdict before proposeTrade; the model can jump straight to staging
One clean switch per messageNone — the model re-decides every turnMode flickers mid-thread; context from one mode leaks into the other
The diagnosis in one sentence
A load-bearing decision — is this message conversation, trade intent, or an order command? — is currently made by the least deterministic component in the system. Everything else in Requi that is load-bearing was moved into code for exactly this reason; the chat mode switch is the last one left in the prompt. This specification moves it.

Non-goals for this fix: no changes to the ticket pipeline, the confirmation gate, proposeTrade's validation, the snapshot, or the tool whitelist — they are correct and stay. The change is a pre-classifier and a conversation state machine in front of the existing runtime, plus an advisory composer that runs the deterministic analysis before any staging is allowed.

3The design: a deterministic intent router

Every incoming chat message passes through classifyIntent() — a pure function, no model call, no network — before the LLM is invoked. The router returns one of four modes, and the mode shapes everything downstream: which prompt addendum is used, which tools are offered, and whether staging is even possible this turn.

message ─► classifyIntent() ─► one of: CHAT default. conversation, questions, analysis, reviews. proposeTrade is NOT offered this turn. TRADE_INTENT an instruction to transact ("buy ...", "sell ...", "flatten ..."). ► enters the advisory-first pipeline (§4). proposeTrade is offered ONLY after the advisory has been delivered. ORDER_COMMAND "CONFIRM ORDER ..." / "REJECT ORDER ..." / "cancel ...". ► handled by the existing confirmation path, no advisory. STATUS_QUERY "what's open / P&L / positions / monitors / tickets". ► data tools only; read-only turn.

3.1 The trigger lexicon (deterministic, versioned, testable)

ClassTriggers (case-insensitive, word-boundary)Notes
ORDER_COMMANDconfirm order · reject order · cancel order · cancel tkt-Checked FIRST — these hit the existing confirmation path verbatim
TRADE_INTENTbuy · sell · long · short · flatten · close (my|the) position · add to · exitMust co-occur with a symbol token (or an open position, for exits) to qualify
STATUS_QUERYp&l · positions · orders · tickets · monitors · what's open · how am i doingRead-only tools only
CHATEverything else — including market opinions, "what do you think", strategy questions, post-trade reviews

3.2 Negation & question guards — where routers usually break

A trigger word inside a question or a conditional is not an instruction — it's conversation ABOUT trading, and the correct mode is CHAT with a full analysis (the user is asking "good buy or bad buy?"). The guard is deliberately simple and conservative:

MessageModeWhy
"buy Apple"TRADE_INTENTimperative + symbol
"buy 100 Apple"TRADE_INTENTimperative + quantity + symbol
"should I buy Apple?"CHAT (+analysis)question form — advise, don't stage
"is it a good time to buy?"CHAT (+analysis)question form
"what happens if I buy here?"CHAThypothetical
"don't buy yet"CHATnegated imperative — acknowledge, stand down
"why did it buy?"CHAT (post-trade review)past tense — review, not instruction
"okay, do it — buy it"TRADE_INTENTimperative; "it" resolves to the symbol under discussion (§5 context)
"CONFIRM ORDER TKT-12345"ORDER_COMMANDexisting confirmation path
Conservatism rule
Ambiguous → CHAT. A missed trade intent costs the user one more sentence ("yes, buy it"); a false trade intent costs a staged ticket they never asked for. The router always errs toward conversation.

4Advisory-first: the trade-intent pipeline

When the router returns TRADE_INTENT, the turn runs a fixed sequence in code. The model's only job in this mode is to narrate the result honestly. Nothing can be staged before the advisory exists — the tool list for this turn simply doesn't include proposeTrade until step 4 completes.

TRADE_INTENT(message) │ ├─ 1. EXTRACT symbol · side · quantity? · stop? (deterministic parse) │ └─ symbol missing/ambiguous → ask, stay in ADVISORY │ ├─ 2. ANALYZE marketDataService.track(symbol) → indicators │ scanner.identifyStrategy(feed) → best-fit setup + confidence + reasons │ data checks (§5 spec): fresh feed? enough bars? market open? │ └─ stale/missing data → verdict UNFAVORABLE with the exact reason │ ├─ 3. PROTOCOL governance package active? risk preview via sizePosition() │ CHECK portfolio heat gate · correlation gate (same functions the │ monitor uses — one implementation, two callers) │ └─ any gate blocks → verdict BLOCKED with the gate's verbatim reason │ ├─ 4. VERDICT compose Advisory: │ FAVORABLE — setup identified, gates pass, data fresh │ WAIT — no setup yet; includes WHAT TO WATCH + when to re-ask │ UNFAVORABLE — data/quality reasons │ BLOCKED — a protocol gate forbids it (heat, correlation, governance) │ ├─ 5. NARRATE model receives the Advisory object + snapshot and writes │ the answer in plain language — verdict, evidence, proposed parameters, │ and "say the word and I'll stage it" │ └─ 6. STAGE ONLY on a follow-up imperative ("do it", "stage it", "buy") (opt-in) does the next turn offer proposeTrade → ticket → CONFIRM

4.1 The Advisory object (the contract between code and narration)

interface Advisory {
  symbol: string; side: "BUY" | "SELL";
  verdict: "FAVORABLE" | "WAIT" | "UNFAVORABLE" | "BLOCKED";
  reasons: string[];              // verbatim engine evidence — trigger states, gate reasons
  dataQuality: { fresh: boolean; bars: number; marketOpen: boolean; delaySeconds: number };
  setup: { strategyId: string; confidence: number; state: string } | null;
  sizingPreview: { qty: number; dollarRisk: number; cappedBy: string } | null;
  proposed: { entry: number | null; stop: number | null; target: number | null } | null;
  watchFor: string | null;        // WAIT verdicts: exactly what would change the answer
  governanceVersion: string;
}

4.2 What the user experiences

User: "buy Apple" TRADE_INTENT

Intelligence: "Analysis before anything is staged — Apple is trading 0.8% above VWAP with RSI 61; the engine's best-fit setup is VWAP-reclaim but the hold-timer hasn't confirmed (6 of 10 minutes). Verdict: WAIT — a confirmed hold for 4 more minutes flips this to favorable. Proposed when it confirms: entry 214.30 stop 211.80 (risk 0.5% of equity, 200 shares). Say 'stage it' and I'll put the ticket up, or ask me anything else first."

User: "actually what do you think of the overall market?" CHAT — the switch works

Intelligence: normal conversation, full snapshot available, zero trade framing.

User: "okay stage it" TRADE_INTENT (follow-up imperative)

Intelligence: "Staged — ticket TKT-4471. Reply exactly CONFIRM ORDER TKT-4471 to authorize, or REJECT ORDER TKT-4471 to cancel. Nothing reaches a broker until you confirm."

Why advisory-first is the institutional pattern
It mirrors the risk-desk workflow the whole platform is modeled on: analysis → desk check → recommendation → execution authorization. It also kills the two symptoms at once: "buy X" no longer hijacks the thread (the advisory closes with an invitation, not an interrogation), and a conversational user who says "do it" gets a deterministic escalation path instead of hoping the model notices.

5The conversation state machine

Mode is per-message from the router; context is per-thread from a small state machine. This is what makes "it", "stage it", and "cancel that" resolve correctly without asking the model to remember.

┌────────────────────────────────────┐ ▼ │ CONVERSING ──TRADE_INTENT──► ADVISORY ──follow-up imperative──► STAGED ▲ │ │ │ │ "never mind" / timeout │ CONFIRM / REJECT │ ▼ ▼ └──────────────────────────┴──────────────────────────────────┘ (always lands back in CONVERSING) STAGED holds: ticketId, symbol, side, proposed params, advisory, expiresAt (5:00)

5.1 State contents & rules

StateWhat the thread remembersRules
CONVERSING (default)last discussed symbol (if any)proposeTrade never offered; all read tools available
ADVISORYthe Advisory object + symbol/side under discussion"it" / "that" resolves to the advisory symbol; "stage/do it/buy it" escalates to STAGED; any new topic returns to CONVERSING
STAGEDticketId + expiryonly ORDER_COMMAND or cancel language applies to the ticket; expiry (5:00) auto-returns to CONVERSING with a one-line notice

5.2 The clear switch, stated as invariants

  1. Default is CHAT. Every thread starts CONVERSING; every completed or expired trade flow ends CONVERSING.
  2. One mode per message, chosen by the router — never mid-turn, never by the model.
  3. Staging requires an imperative in TRADE_INTENT mode. Questions, conditionals, and hypotheticals can never stage.
  4. Advisory precedes staging. proposeTrade is physically absent from the tool list until an Advisory exists for that symbol+side in this thread.
  5. Timeouts are loud, not silent. An expired staged ticket says so in one line and stands down.
Persistence
Thread state lives in the existing chat memory layer (per user, per thread, JSON blob beside the message history). No new tables: chatState = { mode, advisory?, stagedTicketId?, expiresAt? }. On any read error the state defaults to CONVERSING — fail-safe toward conversation.

6Implementation guide — files, functions, wiring

Sized for one focused engineer: one new module, two small edits to existing files, one prompt edit. Nothing in the ticket pipeline, confirmation gate, or tool executors changes.

6.1 New file: api/intelligence/intent.ts (~200 lines)

ExportContract
classifyIntent(message, threadState)Pure function → { mode: "CHAT" | "TRADE_INTENT" | "ORDER_COMMAND" | "STATUS_QUERY", symbol?, side?, quantity?, reason }. Lexicon + negation/question guards from §3. Word-boundary regex; symbol = 1–5 uppercase letters or a known tracked symbol; "it/that" resolves from threadState.advisory.
TRADE_TRIGGERS / STATUS_TRIGGERS / COMMAND_TRIGGERSExported constants — the versioned lexicon. Changing a trigger is a code edit with a test, never a prompt edit.
composeAdvisory(userId, symbol, side)Runs §4 steps 2–4: track → indicators → identifyStrategy → governance status → sizePosition preview → portfolioHeatPct / returnCorrelation gates (imported from api/engine/risk.ts — the same functions the monitor uses). Returns the Advisory object; never throws on data failure — returns UNFAVORABLE with the reason (§5 spec never-estimate rule).

6.2 Edit: api/intelligence/tools.ts — the chat loop (three precise changes)

  1. Route before the loop. First statement of the chat handler: const intent = classifyIntent(message, threadState). Branch on intent.mode.
  2. Per-mode tool lists. CHAT/STATUS_QUERY → all read tools, proposeTrade removed. ORDER_COMMAND → bypass the model entirely, straight to the existing confirmation path (exact-string handling already lives there). TRADE_INTENT → first call composeAdvisory(), inject the Advisory object into the snapshot, and offer proposeTrade only when the thread already holds a matching advisory (follow-up imperative) — otherwise the turn ends after narration.
  3. Thread state write-back. Persist { mode, advisory?, stagedTicketId?, expiresAt? } via memory.ts beside the message; on any read error default to CONVERSING.

6.3 Edit: RUNTIME_ADDENDUM — Rule 2 replaced

The prompt stops being the router. Rule 2 becomes narration discipline, not mode selection:

2. MODES ARE SET BY THE SERVER, NEVER BY YOU. Each turn arrives with a mode:
   CHAT — converse normally; you have no staging tool this turn.
   TRADE_INTENT — an ADVISORY object is in your snapshot. Narrate it faithfully:
   verdict, the engine's evidence (every reason string), proposed parameters, and
   close with "say 'stage it' and I'll put the ticket up". Never invent numbers
   beyond the object; never skip to staging language the object doesn't support.
   STAGED — show the ticket id and the exact CONFIRM/REJECT strings. Say "staged",
   never "bought/sold/executed".

6.4 What is deliberately NOT touched

  • proposeTrade executor and its validation (stop required, quantity bounds, origin INTELLIGENCE) — correct as-is.
  • The confirmation path and exact-string governance check — ORDER_COMMAND routes to it unchanged.
  • buildSnapshot() — the Advisory object is appended per-turn, the base snapshot is unchanged.
  • Autonomous engine, monitors, trailing — this feature is Intelligence-module only.
Effort & risk
~1 day including tests. Risk: LOW — additive layer in front of a stable runtime; worst-case fallback is a feature flag (INTENT_ROUTER=off) that restores current behavior by skipping the classifier and offering today's full tool list.

7.2 Advisory quality tests

  1. Data failure honesty. Symbol with a dead feed → verdict UNFAVORABLE, reason = the feed's error string, sizingPreview null.
  2. Gate passthrough. Heat at 9.8% + proposed 0.5% risk → verdict BLOCKED with the heat gate's verbatim reason — the same string the monitor would produce.
  3. Market closed. dataQuality.marketOpen=false → verdict WAIT with "market opens 09:30 ET" in watchFor.
  4. No setup. identifyStrategy returns nothing → WAIT with watchFor describing the missing condition in plain language.

7.3 Conversation-flow test (the owner's two symptoms, as scripted UAT)

  1. "buy Apple" → advisory narrated, then "what do you think of the market?" → clean conversation with no trade framing. Symptom 1 dead.
  2. Long conversation → "okay, do it" → deterministic escalation to advisory/staging without the model guessing. Symptom 2 dead.
Definition of done
7.1 all green · 7.2 all green · 7.3 both scripts pass on screen recording · no changes observed in the ticket pipeline's behavior (existing trades flow identically) · feature flag documented in the runbook.

FileChange

NEW (~230 lines)		 The deterministic router. classifyIntent(text, thread) → five modes: CHAT (default), TRADE_INTENT, ORDER_COMMAND, STATUS_QUERY, STRATEGIZE. api/intelligence-router.ts
EDIT		 The chat endpoint wires the router behind the feature flag (process.env.INTENT_ROUTER !== "off"). STRATEGIZE → the existing strategy-builder branch. CHAT / STATUS_QUERY → agentChat with the write tool removed. If the model is unreachable, a deterministic fallback narrates the engine's verdict directly — the numbers still come from the engine.

8.3 Deployment steps (production)

  1. Snapshot / pull the release at version 656528f. Confirm the three files above are present and the working tree is clean.
  2. Environment: OPENAI_API_KEY set (required for narration); OPENAI_MODEL optional (default gpt-5.6); leave INTENT_ROUTER unset — the router is ON by default. Set INTENT_ROUTER=off only to roll back.
  3. Build: rm -f *.tsbuildinfo && npm run build → expect the Vite client build and dist/boot.js (~3.7 MB) with no type errors.
  4. Verify the bundle carries the router (all four must print a non-zero count):
    grep -c classifyIntent dist/boot.js · grep -c composeAdvisory dist/boot.js · grep -c allowTradeTool dist/boot.js · grep -c INTENT_ROUTER dist/boot.js
  5. Restart production: stop the old process, then NODE_ENV=production setsid nohup node dist/boot.js > /tmp/boot.log 2>&1 < /dev/null &
  6. Boot log: expect [db] schema ensured and Server running — no stack traces.
  7. Smoke contract: root returns 200; signed-out POST /api/trpc/intelligence.chat returns 401 (a 404 means a stale deploy — rebuild). Note the mount path is /api/trpc.
