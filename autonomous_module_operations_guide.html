1Paper mode vs. live mode — the one-paragraph answer

Paper mode means the platform runs the complete trading pipeline — scanning, state machines, risk gates, tickets, confirmations, fills, positions, trailing stops, P&L — but the "broker" on the ticket is PAPER: a simulated execution venue inside our own server. Fills are computed, not received; the account is a fixed paper equity of $100,000 used for position sizing; no money exists and nothing leaves the building. Live mode means the ticket's broker is a real connected broker account — today IBKR (Interactive Brokers, via the TWS/Gateway over the Model Context Protocol). The identical pipeline runs, but the order is transmitted to IBKR, the fill comes back from the exchange, the position is real, and the P&L is real money. The engine does not have two code paths. It has one pipeline with a broker field on the ticket — and that field is the mode.

1.1 Side by side

1.2 Why the modes can never silently mix

Every position inherits its mode at fill time from the ticket that created it — copied onto the position row itself (positions.broker). From that moment the mode is a fact of the data, not a UI setting: order history shows it, the positions table shows it, and the P&L engine splits on it. A paper position can never be marked as live and a live position can never be averaged into a paper one, because the mode travels with the row, not with a toggle.

Current default
Today the Intelligence chat proposes with broker = PAPER, and the autonomous engine proposes paper tickets until a live broker account is bound. If a real broker call degrades mid-flight, the system falls back to paper and says so on the ticket ("paper fallback" in the confirmation message). Nothing ever silently pretends to be live.

2The golden rule: everything is a ticket (data lineage)

There is exactly one way for any trade to exist in Requi — whether it came from the Intelligence chat, the Autonomous engine, or a human clicking manual order: it becomes an order ticket, and only a ticket may reach a broker. Once you know the lineage, every screen and every number in the product is just a view over the same chain:

INTELLIGENCE (chat) ─┐ AUTONOMOUS (engine) ─┼─► proposeTicket() ─► order_tickets row (state: CREATED) MANUAL (operator) ─┘ │ broker = PAPER | IBKR ← THE MODE ▼ CONFIRM string (or auto-execute, AUTONOMOUS only) ▼ SUBMITTING → WORKING → FILLED (or FAILED/REJECTED/EXPIRED) ▼ recordFill() ─► positions row (broker copied from ticket ← MODE LINEAGE) ▼ ┌──────────────────────────┼───────────────────────────┐ ▼ ▼ ▼ ORDER HISTORY POSITIONS & PROTECTION P&L & METRICS engine.orders engine.positions engine.pnl (tickets where (open rows marked to feed; (realized from CLOSED rows, state ≠ CREATED) trailing engine guards them) unrealized from marks) └──────────────────────────┴───────────────────────────┘ ▼ REPORTING — always splittable by mode: pnl.byMode.paper · pnl.byMode.live

2.1 The five facts that make the lineage trustworthy

  1. One writer per stage. Only proposeTicket() creates tickets; only the confirmation/auto-execute path submits them; only recordFill() opens positions. Three functions, one chain — there is no side door.
  2. The position remembers its ticket. positions.sourceTicketId points back to the ticket that opened it; positions.broker freezes the mode at fill time.
  3. Scale-outs keep the parent's mode. When a T1/T2 scale-out closes part of a position, the closed child row carries the original position's broker — never the sell ticket's.
  4. Order history is tickets, not a separate log. The Orders panel is literally the ticket table minus unsubmitted drafts — so "did the order connect?" is answered by one row's state field.
  5. P&L is computed from positions, never from tickets. Realized P&L comes only from CLOSED position rows; unrealized comes only from open rows marked to the live feed. Tickets tell you what was attempted; positions tell you what is true.
How to audit any trade in 30 seconds
Find the ticket in Orders → note its state and broker badge → find the position it opened (sourceTicketId) → its broker badge matches the ticket's → its realized/unrealized P&L appears in the matching mode bucket of the P&L panel. If any link is missing, §6 (Troubleshooting) has the exact failure table.

3Mode lineage — how paper/live is marked everywhere

This release (snapshot 4896a72) makes the mode visible at every layer of the stack. The rule the whole system now obeys: a number on any screen must be answerable to one mode or be an explicit, labeled combination of both.

3.2 What the mode badges mean operationally

  • PAPER — simulated fill, $100k paper equity sizing, no broker-side disaster stop, no money at risk. Used for validation, demos, UAT, and the engine's default until a live account binds.
  • LIVE — real broker execution, real equity, resting disaster stop at IBKR, real P&L. Every protection (governance, gates, CONFIRM, trailing) is identical.

3.3 The three mode questions you can now answer instantly

  1. "Is this trade real?" → look at the badge on the ticket or position. Badge is the mode; the mode is the broker column; the column is set once at fill time and never edited.
  2. "What did we make on paper vs live?" → the two mode cards under P&L. They never mix.
  3. "Did anything trade live that shouldn't have?" → SELECT * FROM positions WHERE broker != 'PAPER' — if the answer surprises you, §6.7 is the incident path.
Pre-existing rows
Positions created before this release have no broker value on the row; the guarded migration backfills them to PAPER — which is factually correct for every fill this platform has produced to date (no live account has been bound). If a live account was bound before this release, update those rows manually using the ticket lineage (sourceTicketId → order_tickets.broker) — SQL in Appendix A.4.

The three classic "wrong metrics" bugs — and why they can't happen here
1. Mixing attempted with executed — impossible: metrics read positions, attempts read tickets, different tables. 2. Mixing paper with live — impossible as of this release: every row carries its mode and the split is structural. 3. Inventing marks — impossible: unmarked rows are excluded and disclosed, never estimated (§5 of the Strategy Specification). If a metric ever seems wrong, first check which mode bucket you're looking at and whether the position is marked — those two checks resolve 95% of "wrong number" reports.

The two rules of Requi troubleshooting
1. Read the reason string first. The engine narrates every refusal — gates, monitors, tickets all carry a verbatim reason. The message is the diagnosis; don't guess around it. 2. Never "fix" by editing data. Numbers are derived from the ticket→fill→position chain. If the chain is wrong, fix the chain; if the number is wrong, find which link disagrees. Editing a derived number destroys the audit trail and converts a bug into a lie.

A.1 Mode-lineage audit (the 30-second trade audit)

-- Trace one position back to its ticket and confirm the modes match
SELECT p.id, p.symbol, p.broker AS position_mode,
       p.sourceTicketId, t.broker AS ticket_mode, t.state, t.averageFillPrice
FROM positions p
LEFT JOIN order_tickets t ON t.ticketId = p.sourceTicketId
ORDER BY p.id DESC
LIMIT 20;
-- PASS rule: position_mode = ticket_mode on every row.

A.2 Mode-separated P&L (server computes this — use it to cross-check)

SELECT broker AS mode, status,
       COUNT(*) AS rows_n,
       ROUND(SUM(COALESCE(realizedPnl, 0)), 2) AS realized
FROM positions
GROUP BY broker, status
ORDER BY broker, status;
-- Compare against the Paper/Live cards on the P&L panel. Must agree.

SET p.broker = t.broker
WHERE p.id = <position_id> AND t.broker != 'PAPER';

B.5 api/engine/portfolio.ts — mode-aware P&L split

export interface ModePnl {
  realizedTotal: number;
  unrealizedTotal: number;
  openCount: number;
  closedCount: number;
  winCount: number;
  lossCount: number;
}

function summarize(rows: PositionRow[]): ModePnl {
  /* Mode-aware reporting: paper and live P&L are ALWAYS separable.
   * Combined totals above remain for back-compat; the byMode split is the
   * authoritative view — a position's mode is fixed at fill time from its
   * source ticket's broker (PAPER | live broker name). */
  const byMode = {
    paper: summarize(rows.filter((r) => r.broker.toUpperCase() === "PAPER")),
    live: summarize(rows.filter((r) => r.broker.toUpperCase() !== "PAPER")),
  };
